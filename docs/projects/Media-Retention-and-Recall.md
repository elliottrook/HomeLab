## Purpose and desired outcome

Keep a useful, good-quality film and TV Archive without filling the `Media` pool. Existing Radarr/Sonarr acquisition profiles continue. A movie or whole TV season enters the Archive view and is eligible for quality-led optimization after three calendar months. Archive media has a 1080p maximum, genuine HDR and 5.1 when the source has them, one suitable English audio track, and all English subtitle variants. **45 decimal MB/minute (0.75 MB/s, 6 Mb/s total)** is a soft planning and anomaly reference, not a hard size cap or an instruction to recompress satisfactory files. Preserve playable legacy sources until a genuine upgrade exists.

At 60% raw `Media` pool allocation, remove the oldest eligible Archive media that no household user has watched, partly watched, favorited or marked to keep. Preserve at least one physically present movie from **every release year** represented in the complete household movie library, including Current and Archive; re-evaluate that count after each removal. Aim back near 60%; alert at 62% if intake outruns safe reclamation. Keep each removed title in ARR but unmonitor the selected movie or season so it is not immediately reacquired. Offer an explicit household request path for unavailable titles, with an AsterTV card and short local status clip as the preferred first client; test a native Jellyfin marker separately.

## Authority model and architecture

| Fact/action | Authority and boundary |
|---|---|
| Pool allocation, snapshots, actual freed bytes | TrueNAS ZFS; raw `Media` pool is the trigger |
| Title, file and monitoring state; bounded search | Radarr/Sonarr; server-side restricted adapter only |
| Watch/progress/favorite state and real playback | Jellyfin, queried across all seven household users; fail closed on missing data |
| Household request | Seerr; AsterTV is a client, never an ARR-key holder |
| Age, candidate decision, cooldown and audit | Durable source-local lifecycle ledger/controller, keyed by provider, ARR and file identity |
| English subtitles | Probed file and sidecar manifest; Bazarr is an additive source |
| Current/Archive and requestable UI | Accepted lifecycle view contract and AsterTV/Jellyfin client evidence |

Persist **first-ever title acquisition** separately from **current-file import**. The first orders eviction; the second starts a three-calendar-month movie or youngest-present-episode season clock. An optimizer replacement must not reset its own clock; a genuine upgrade or fulfilled re-request does. For legacy titles with no provable first-acquisition date, Jason approved a **media-date fallback for eviction order only**: original movie release date/year, or the season's earliest original episode air date; if that is unavailable, the series' original first-air date. Mark the provenance and precision (`acquired`, `movie-release`, `season-air`, `series-air`), never silently promote a release date to an acquisition fact, and break same-date ties by stable provider ID. A title with no credible media date stays held. This fallback never makes a newly imported file three months old. Inventory and compare exact file paths, provider IDs, ARR file records, user watch state and subtitle sidecars before any action.

Run one policy controller daily with an exclusive lock. At 60% select prevalidated, never-watched Archive candidates in first-acquisition order. Movie is one unit; TV is whole-season scope while other seasons remain monitored. Build a complete, deduplicated, physically present and provider-verified movie-year inventory across Current and Archive; an unknown year/count holds that movie. Before each movie removal, verify that at least one *other* movie of the same release year will remain. Recheck all facts immediately before a bounded action; unmonitor the selected ARR scope, remove its file through ARR, then verify ARR tombstone, physical bytes, Jellyfin rescan and actual ZFS use. Stop near 60%, with 62% as an urgent alert and intake-review threshold. Do not continue deleting merely because snapshots or a recycle bin retain blocks. No watched, partial, favorite, keep, unknown, duplicate/conflicted, active playback or active download item may be selected. A request grants a cooldown and cannot be evicted immediately on return.

Jason selected a **three-day minimum household notice period** on 2026-11-06. The dry-run selector holds a title without a verified notice timestamp bound to the current file identity, or while its three full days are still running. Sending and recording a real household notice is not yet implemented, so this guard cannot be satisfied in production today. The future source adapter must invalidate an old notice when its file identity changes.

Jason chose [AsterTV as the household notice and Keep route](Media-Retention-AsterTV-Notice-Contract.md). The server-side contract is a local design candidate. AsterTV v3 remains Stream M; this Stream A decision does not authorize changing or deploying that client. No current v3 development agent was found in the available active Codex chats on 2026-11-06; coordinate with its owner before client implementation.

An indexed year count is not enough on its own: count only distinct films with a physical file, matching Radarr/Jellyfin provider, path and release year, and visibility to every current household user. A complete scan can yield a conservative lower bound when some films are held. Require at least two such verified films before one may be removed. For legacy titles, Jason accepted the complete current seven-user Jellyfin state **plus all retained playback logs** as the available unwatched evidence, while acknowledging that pre-migration history cannot be proven. Any watched, partial, favorite, keep or retained playback signal protects the item; an incomplete user or log scan holds it. A file held in any retained `Media/data` snapshot has zero immediate reclaim estimate and is ineligible until a separately accepted recovery/snapshot policy changes that fact. Snapshot deletion is not part of the M4 controller's automatic actions. The [review-only snapshot expiry proposal](Media-Retention-Snapshot-Expiry-Policy.md) records the separate recovery decision required before any named snapshot is released.

For recall, prefer an authenticated AsterTV catalog card backed by retained provider/ARR identity. A deliberate **Request again** action asks the server-side adapter to validate headroom, cooldown and idempotence, lodge/restore the Seerr request, re-monitor the correct ARR scope and issue one bounded search. Only then play a locally generated reusable six-to-ten-second status clip using Aster's canonical Kokoro ONNX `bm_daniel` en-gb voice at 0.95 speed, with the accepted speech cleanup/cadence. Remove the card after ARR, Jellyfin and playback verify the real file. A native Jellyfin placeholder is a separate lab experiment because a fake playable item can corrupt availability and watch semantics.

## Privacy and security design

Keep household watch data and title-level deletion logs source-local; put only aggregate, sanitized evidence in Git. Use existing private service paths and least-privilege server-side credentials outside Git. A playback GET or preview must never trigger an ARR write; require explicit authenticated request intent, rate limit, idempotency and an operator recovery route. No DNS, firewall, certificate or public-path change is planned. Follow the [Aster internal UI style guide](../design/HomeLab-UI-Style-Guide.md) for the request card and the repository's canonical voice standard for the clip.

## Pre-start risk assessment and accepted boundary

| Risk (likelihood/impact) | Control, abort and recovery |
|---|---|
| Last-copy loss or wrong-title deletion (medium/critical) | No production removal until exact identity, ARR ownership, subtitle manifest, protected checkpoint and isolated restore prove; one movie and one season pilot, then capped batches. Abort on mismatch. |
| Incomplete watch history, unknown original age or shared series identity (high/high) | Fail closed on watch or identity unknowns; compare seven users and migration evidence. For missing acquisition dates use only the explicitly approved, labeled media-date fallback after provider/date validation; no ranking by mtime. |
| Pool use fails to fall because of snapshots/recycle bin (high/medium) | Verify actual ZFS allocation between batches; alert and stop rather than cascade deletion. Account for Current intake and pending downloads. |
| ARR reacquires deleted items or fails to reacquire on request (medium/high) | Verify per-movie/season monitoring and RSS/search behavior in a disposable lab, then reversible pilot; rollback monitoring and file from checkpoint. |
| Missing media card falsely shows availability or clip triggers a request (medium/medium) | Prefer AsterTV explicit action; no write on playback; test real Kodi/Jellyfin clients and Seerr state. |
| Credential or private viewing-history leakage (low/high) | Source-local ledger, restricted adapter, secret-pattern review, aggregate Git logs. |
| Household browsing disruption or backup contention (medium/medium) | Run bounded off-peak jobs, retain old views and client rollback, Doctor alert and abort on unhealthy dependencies. |

No planned network or external-service change. A controller cannot guarantee the 60–62% band when safe candidates are exhausted, downloads surge, or snapshots retain blocks. It must report this and stop; it must never relax protection automatically. Before destructive production work, inspect current application versions, backups, snapshot coverage, restore space, ARR/Jellyfin recovery order, dataset accounting, request consumers and the AsterTV v3 candidate. The pre-start assessment is accepted for M0 read-only discovery and local implementation under Jason's Stream A direction; the untested last-copy deletion stop condition remains in force.
