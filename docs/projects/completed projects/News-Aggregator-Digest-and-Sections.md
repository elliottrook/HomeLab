## Purpose and desired outcome

Phase 1 delivered an hourly "breaking news" clustered feed. Jason asked for
three additions on top of it, without disturbing the breaking-news view:

1. A twice-daily (06:00/18:00) richer digest per cluster: an **abridged,
   multi-source synthesis** plus, for multi-outlet clusters, **deviation
   notes** — what one source says that the others don't — generated by the
   same `aster-llama` endpoint and dedicated key Phase 1 already uses.
2. A redesigned card layout for that digest view specifically (hero image
   when the feed provides one, outlet-badge header when it doesn't, styled
   after the Apple News "Top Stories" card Jason shared), while the existing
   breaking-news view stays exactly as it is today.
3. A settings page where Jason can request a new source, or a whole new
   **section** (e.g. "add a photography section with these sources") —
   queued for the same live-verification pass every feed has gotten since
   Milestone 2 of Phase 1, not auto-added to `feeds.json` unverified.

Explicitly out of scope for this phase (Jason's own words): scraping outlet
pages for better photo coverage stays deferred to a possible Phase 3, not
built now.

  LXC 114 guest, existing SQLite database, and existing `aster-llama`

  `digest.py` pipeline stage, a new systemd timer/service pair, new Flask
  routes and templates in the existing `app.py`, and structured `section`

  permitted, same VLAN) and the RSS/Atom feed URLs Jason approves through

  Homepage change is anticipated — nothing new is being exposed or
  relocated. HomeLab Doctor's existing `check_news_aggregator()` will be
  reviewed for whether it needs a digest-specific addition, not replaced.
- **Non-waivable stop condition preserved:** see the checkpoint above (a
  requested source with no clean feed).
- **Backup:** already covered automatically — Phase 1's whole-guest backup
  (local Proxmox snapshot plus the checksum-verified TrueNAS off-host pull)
  captures the entire LXC 114 filesystem, so new tables in the same
  `news.db` and new files under `/opt/news-aggregator/` need no separate
  backup step.

## Operations quick reference (Phase 2 additions)

Supplements Phase 1's own Operations quick reference in
`completed projects/News-Aggregator-MuckScraper.md` rather than editing
that closed document.

- **Digest view:** `http://192.168.70.13:8080/digest` (or the "Digest" nav
  button from any page).
- **Settings/source-request view:**
  `http://192.168.70.13:8080/settings` — queues requests in
  `source_requests`; never edits `feeds.json` directly. Adding a requested
  source for real still means the same manual verify-then-edit-`feeds.json`
  workflow Phase 1 established.
- **Trigger a digest run on demand** (e.g. to test after a code change,
  without waiting for the 05:15/17:15 schedule):
  `pct exec 114 -- systemctl start news-aggregator-digest.service`. It's a
  oneshot service, so `systemctl start` blocks until the run finishes.
- **Digest schedule:** `news-aggregator-digest.timer`, fixed at
  `Etc/GMT+7` (BC no longer observes DST) so it doesn't drift across
  seasons. If BC's fixed offset ever turns out to be UTC-8 instead of
  UTC-7, edit the timer unit's `OnCalendar` line directly — see the
  comment in the unit file for the exact change needed.
- **Digest data:** `digest_entries` table in `news.db` — one row per
  multi-outlet cluster, replaced (not appended) each time that cluster
  gains new coverage.
- **Pending source requests:** `source_requests` table, or just the
  Settings page itself.
