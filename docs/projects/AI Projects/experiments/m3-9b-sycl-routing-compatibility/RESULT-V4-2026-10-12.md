# M3 9B/SYCL routing compatibility v4 — synthetic development result

**Decision: format-compatible, semantically unqualified.** Keep the local
model out of automatic capability routing. This result does not assess its
ordinary answer quality or general sysadmin ability, and it does not change
the accepted inference service. The next routing-quality test needs new,
independently accepted human labels and a frozen comparison against the
deterministic baseline; do not keep tuning this prompt on these 30 exposed
examples and call the score a holdout.

After v1 stopped at its first invalid response, two separate single-case
diagnostics narrowed the interface problem to a non-`plan` status carrying a
capability. The frozen [v4 card](RUN-V4-CARD.md) added one explicit prompt
rule: `clarify` and `abstain` must carry an empty list. No parser, schema,
model, capability vocabulary, tool permission or production setting was
relaxed. Nine local mocked tests passed before the call.

runner made 30 serial calls on the pinned synthetic development fixture. It
used the local mode-0600 key file inside LXC 110 and sent no key, tool,
personal context or answer labels to the model. The [content-free result](run-v4-2026-10-12.json)
has SHA-256 `20d75242c9057008eeaa99ca2749eb17845334424debbe6cc65673c8ddf47303`.

All three calendar and all three mixed calendar/web cases were missed, as were
all three private-context cases. The local model mostly chose `clarify` for
them, despite the experiment asking for *required capability IDs*, not the
data itself. One household-control case abstained, and one media and one
sysadmin case unnecessarily clarified. Timer, facts, web and intentionally
ambiguous examples matched 3/3 in each family. These tiny family counts are
diagnostic clues, not stable rates or a basis for threshold calibration.

The system prompt says the model has no access to personal data. **Hypothesis,
not established cause:** the model may have interpreted that execution limit
as a reason to refuse a capability proposal for calendar/personal requests.
Testing that explanation would require a new preregistered prompt and fresh
evaluation data; tuning to make these exposed examples pass would contaminate
the quality claim. The deterministic policy and capability registry should
continue to govern privacy and authority regardless of any model route.

The inference service was healthy before and after: same PID 7049, zero
recorded restarts, `/health` OK, and zero processing/deferred requests at
the sampled checks. Those snapshots do not prove continuous exclusivity.
No model, gateway, policy, AI-PAM grant or Companion setting was changed. The
closed S1 holdout and D3 manual-Codex release gate were untouched.
