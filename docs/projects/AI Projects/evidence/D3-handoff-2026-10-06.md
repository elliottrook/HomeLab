# D3 gateway/worker handoff candidate — 2026-10-06

## Implemented locally

Two small durable ledgers now model gateway delivery and worker admission.
An immutable envelope binds job, owner, assigned worker, expected gateway,
delivery ID, exact request hash, scope hash, model and dispatch expiry. The
worker requires a locally allowed scope/model pair and checks the payload hash
before first admission. Extra fields, changed assignments and altered payloads
are rejected. Raw prompts and final answers are not stored by these ledgers.

The gateway's internal create operation is **post-policy**: it is not a public
enqueue endpoint or evidence that a human approved an arbitrary request. A hash
is an integrity binding, not a signature or authentication mechanism. Identity
arguments must come from a verified transport dependency, never request JSON.

Repeated offers retain the same delivery ID. The worker commits admission before
execution can be considered. Duplicate delivery or restart returns a duplicate
signal, not permission to dispatch. A never-offered job can expire; an already
offered job instead becomes unknown. Neither is automatically reassigned or
recreated. A five-minute first-dispatch window is enforced independently on both
sides for this bounded pilot.

Receipts are bound to the assigned worker and delivery ID. Late progress cannot
overwrite completion or turn unknown into running. Matching duplicate terminal
receipts are idempotent; conflicting terminal outcomes or result hashes fail.
Completion after a lost receipt can be reconstructed from the admitted envelope,
owner-bound dispatch record and a matching full Codex thread snapshot, without
new inference. Live use must obtain that snapshot through the authenticated
app-server connection; user-supplied transcript JSON is not acceptable evidence.

Both ledgers cap records at 64 by default and fail admission when full rather
than deleting duplicate-prevention history. No automatic archival is introduced.

## Scope and reliability tradeoff

This is at-most-one **admission**, not proof of exactly-once execution across
two machines. Admission before a crash can leave a job uncertain even if nothing
ran. The deliberate response is reconciliation/manual review, not blind replay.
The actual actor must still connect admission to the existing single-owner
runtime, Session/Transport and pinned execution profile. The tests do not prove
that future actor code cannot mistakenly dispatch twice.

Gateway completion means the assigned worker reported/recovered a correlated
terminal result. It is not independent verification of an infrastructure repair
or authority to approve changes. This pilot remains tool-free.

## HTTP boundary candidate

Unregistered, default-disabled worker routes support an offer and a receipt:

- `POST /v1/delegation/worker/jobs/{job_id}/offer`
- `POST /v1/delegation/worker/jobs/{job_id}/receipt`

There is no public job-create endpoint. A dedicated workload-identity dependency
must guard these routes; Companion user authentication must not be substituted.
Receipt schemas forbid additional fields such as worker identity or permissions.
The routes do not launch a model, listen on a port or register with live Aster.
Gateway receipts retain only a result digest; final-answer delivery and its
owner-scoped projection still need integration with the existing status contract.

## Evidence

**102 Python tests and five Node renderer scenarios pass.** New fixtures cover:
lost acknowledgements, repeated deliveries, restart, expired offers, cross-owner/
worker/gateway access, changed scope/model/payload, unknown plans, excessive
lifetimes, stale progress, terminal conflicts, ledger capacity, and completion
recovery across the admission and dispatch ledgers. Five worker HTTP tests use
fixture authentication, not real Authentik credentials.

No new cloud request, live service, worker credential, endpoint, firewall change
or Git push occurred. The successful real Orion D2 result remains unchanged.

## Next integration gate

Stop adding parallel orchestration abstractions. Reuse these contracts to prepare
one disabled vertical integration: existing Companion authorization → approved
fixture job → authenticated outbound Mac worker → existing Codex runner → final
answer/status back to its owner. Inspect existing AI-PAM/Authentik workload
identity options first; specify the narrow scopes and credential custody before
requesting any issuance or deployment. Bind the two ledgers and final-answer
delivery, test transport loss with the local fake provider, then propose one
finite authenticated canary with rollback. Real worker authentication, live
cancellation, usage events and end-to-end UI behavior remain unverified.
